# The Tauri shell hosts the core and carries `ServerMsg` and `Command` as they are

**Status: Accepted.** Approved by the user in the session of 2026-11-15. Not built yet.

Supersedes ADR 0020's process model (`dovetail serve`, clients attaching over the socket) and its toolkit (egui), as `docs/design-v2.md` already states. This ADR adds the how: the wiring, the mapping onto the frontend's `CoreLink`, and how TypeScript stays in step with `dovetail-api`.

## Decision

**1. One process, one core, the existing entry point.** The Tauri app is a new workspace crate at `gui/src-tauri` (package `dovetail-gui`). At start it calls `dovetail_core::spawn`, exactly as `crates/dovetail/src/tui.rs` does, and gets the same `CoreLink`. The core keeps its own thread and its own small runtime; Tauri's runtime never runs core code.

```
 Tauri process
 ├── webview: React
 │     TauriCore.send(cmd)        ──invoke("core_send", cmd)──────────┐
 │     TauriCore.subscribe(fn)    ◄──Channel<ServerMsg>──────────┐    │
 └── Rust shell (gui/src-tauri)                                  │    ▼
       pump thread: for msg in link.messages { channel.send(msg) }    link.commands.send(cmd)
       ───────────────────────── CoreLink (unchanged) ────────────────────────────
       dovetail-core  (its own thread: loop, DB thread, driver, socket)
```

**2. Two calls cross the boundary, and no others.**

| Frontend (`gui/src/core/link.ts`) | Shell | Core |
| --- | --- | --- |
| `send(command)` | `core_send(command: Command)` | `CoreLink.commands.send` |
| `subscribe(fn)` | `core_subscribe(channel)`; a thread forwards every `ServerMsg` | `CoreLink.messages.recv` |

The shell never looks inside a message. On `subscribe` (first load, or a webview reload) it sends `Command::Resync`, so the frontend always begins from a fresh `Snapshot`. A Tauri channel keeps order, which `seq` then checks.

**3. The Rust API is the source of truth for names and shapes.** The frontend's hand-written `core/model.ts` and `core/protocol.ts` were sketched before the Rust types existed (`send_message`, `ChatEntry`, `answer_inbox`). When the real core is wired in they are replaced by generated types, and components move to the Rust names (`Command::Prompt`, `ConversationEntry`, `Command::AnswerPermission`).

**4. TypeScript types are generated by `ts-rs`.** `dovetail-api` gains an optional feature `ts` that derives `TS` on its public types. `cargo test -p dovetail-api --features ts` writes them to `gui/src/core/generated/`, and the files are committed. `scripts/check.sh` regenerates them and fails when they differ, so a Rust change that is not carried over cannot merge. Ordinary builds do not compile the feature.

Before relying on it, a half-day spike: confirm `ts-rs` handles what the API uses (`#[serde(transparent)]` ids, `rename_all`, enums with data, `skip_serializing_if`, and the `serde_json::Value` fields in `InboxKind::Permission`).

**5. `apply` exists twice and is held together by shared cases.** The frontend keeps its own `apply.ts`. A folder of JSON cases (`crates/dovetail-api/tests/fixtures/apply/*.json`: a snapshot, a list of events, the expected snapshot) is run by a Rust test and by a frontend test. A new `Event` needs a new case; both sides fail without one.

**6. Home is the core with no project open.** `Resolution` gains a variant for it: the core opens only `registry.db` and sends a `Snapshot` with `project: None` and the project list. Opening a project reuses today's switch: `Command::OpenProject` → `Event::OpeningProject` → the core stops → the shell spawns a core for that project in the same process and subscribes again. A second window for another project is a second process (as the design says), which already works: each project has its own socket, and `registry.db` is shared safely.

**7. The bridge and the hook stay in the `dovetail` binary.** Sessions need `dovetail mcp` and `dovetail hook`. The shell passes the installed `dovetail` binary as `CoreOptions.exe`; if it is missing the GUI says so and starts no session. `scripts/bootstrap.sh` already installs it.

**8. Closing the window** sends `Command::Quit { end_sessions: false }` and waits for the core as the TUI does. Sessions stop and resume on the next open.

**9. Commands that lend the terminal** (`OpenEditor`, `TakeOver`, `TerminalReleased`) are never sent by the GUI. They stay for the frozen TUI.

## Alternatives rejected

- **`dovetail serve` plus a socket client in the shell (ADR 0020).** Two processes to start, stop and keep in step, for a single-user desktop app. The types are already plain data, so it remains possible later.
- **One Tauri command per `Command` variant.** About sixty hand-written wrappers, each a place to drift from the enum.
- **Send a full snapshot on every change, no `apply` in the frontend.** A chat reply streams about thirty changes a second; each would copy every conversation tail.
- **Compile the Rust `apply` to WebAssembly.** One reducer instead of two, at the cost of a second build toolchain and copying the whole snapshot across the boundary on each event.
- **`tauri-specta` for the types.** Generates the command bindings too, but ties the plain-data API crate to Tauri's ecosystem; the TUI and the mock would compile it for nothing.
- **Hand-written TypeScript types.** How the frontend started; they have already drifted from the Rust names.
- **Tauri events instead of a channel.** Events are broadcast and unordered across windows; a channel is one ordered stream to one subscriber.

## Consequences

- New dependencies, each needing its row in the plan's table: `tauri` (shell only), `ts-rs` (API crate, optional).
- The frontend session's rename from its sketch names to the Rust names is real work; it should happen once, when `TauriCore` lands, not piecemeal.
- The 500 MB memory budget is measured with this wiring in place (design open point 11).
