# Plan: canvases and cards in the core (ADR 0025)

Spec: `docs/adr/0025-canvases-and-cards.md` (its seven decisions are followed as written). Model: how efforts were added (`0017_efforts.sql`, `crates/dovetail-api/src/effort.rs`, `crates/dovetail-core/src/{efforts.rs,db/efforts.rs}`).

Everything new lives in new files (`canvas.rs`, `db/canvas.rs`, `0018_canvases.sql`, ...). Shared files get small additions only, because the multi-repo branch (ADR 0021) is changing them at the same time.

## 1. Storage: `0018_canvases.sql`

The multi-repo branch also wants `0018` (`0018_agent_repo.sql`, uncommitted in its worktree). The contiguity test (`migrations_are_contiguous_and_listed_in_order`) forbids a gap, so a `0019` here would fail `check.sh`; this file is `0018_canvases.sql` and whichever branch lands second renumbers its file (loud: the test fails on a duplicate). Adds three tables, rewrites nothing.

```
canvases   (id, effort_id → efforts, title, framework, created_ms)
cards      (id, effort_id → efforts, canvas_id → canvases NULL = incoming, kind, x, y,
            ref_kind NULL, ref_id TEXT NULL, text, added_by, created_ms)
card_links (from_card → cards, to_card → cards, label, PRIMARY KEY (from_card, to_card))
```

`ref_kind` is one of `finding source decision map task`; `ref_id` is text (maps have text ids). No foreign key on `ref_id` (ADR point 4). Indexes on `cards (effort_id)`, `cards (canvas_id)`.

Tests: migrate an empty database to the latest version, and migrate a database built at version 17 (with an effort and a task in it) and see rows survive and the tables exist.

## 2. API (`crates/dovetail-api/src/canvas.rs`, re-exported)

Types: `CanvasId(i64)`, `CardId(i64)`, `Framework` (`question_tree`, `options_compare`, `free_board`), `Canvas { id, effort, title, framework }`, `CardKind` (`finding source idea decision question map task`), `RefKind` (`finding source decision map task`), `CardRef { kind: RefKind, id: String }`, `Card { id, effort, canvas: Option<CanvasId>, kind, x, y, reference: Option<CardRef>, title, text, missing, added_by, created_ms }`, `CardLink { from, to, label }`, `NewCard { effort, canvas, kind, x, y, reference, text }`.

`title` is always filled by the core: for a reference, the target's title (finding label, source locator, decision text, map title, task title); for an idea or question, its first line. `text` is the card's own words and is empty for a reference. `missing` is true when the target row is gone; the title then reads "(missing)". `x`, `y` are canvas pixels and mean nothing while `canvas` is `None`.

`Snapshot` gets `canvases`, `cards`, `card_links` (`#[serde(default)]`).

Commands: `CreateCanvas { effort, title, framework }`, `RenameCanvas { id, title }`, `AddCard { card: NewCard, link_from: Option<CardId> }`, `PlaceCard { id, canvas, x, y }`, `MoveCard { id, x, y }`, `DeleteCard { id }`, `DropIncoming { id }` (refused for a placed card), `LinkCards { from, to, label }`, `UnlinkCards { from, to }`, `CardFromReply { agent, entry, effort }` (copies the entry's text into an idea card in the effort's incoming), `LoadCard { id }`.

Events: `CanvasUpserted(Canvas)`, `CardUpserted(Card)`, `CardRemoved(CardId)` (apply also drops the card's links), `CardLinked(CardLink)`, `CardUnlinked { from, to }`, `CardLoaded { id, body }` (changes nothing in the snapshot, like `ResearchLoaded`).

`apply()` handles each. Shared cases in `tests/fixtures/apply/canvas.json`, generated by `apply_cases.rs` with `DOVETAIL_BLESS=1` and replayed by the GUI's `apply.test.ts`. TypeScript types are regenerated by the ts-rs export test.

## 3. Core

- `crates/dovetail-core/src/db/canvas.rs`: `impl Db` typed methods running on the DB thread: `load_canvas_state`, `create_canvas`, `rename_canvas`, `add_card`, `place_card`, `move_card`, `delete_card`, `link_cards`, `unlink_cards`, `load_card_body`, `add_finding_card`. `add_card` checks in the same request that the effort exists, the canvas belongs to that effort, and the reference target exists. Links need two cards of one effort.
- `crates/dovetail-core/src/canvas.rs`: `Core` handlers, one per command, each writing through the DB thread then emitting the event; the core keeps no copy of cards (the snapshot builder asks the DB at open and `Resync` reads what `load` returned at open plus events: see below).
- Restore on open: `load_canvas_state` runs next to `load_efforts` and its result is kept on `Core` (`canvases`, `cards`, `links`, like `efforts`) so a snapshot can be built without waiting on the DB.
- Findings: after `file_finding` (round capture) and `file_unfiled_to_task` succeed, the core calls `add_finding_card(task, finding)`, which puts one `finding` card in the task's effort's incoming (`added_by` = the finding's agent id) and emits `CardUpserted`. Findings filed in Tangents are not carded (Tangents has no canvases in the GUI).
- Ids stay valid: nothing deletes finding, source, decision, map or task rows already.

## 4. Agent tools

New suite `canvas` (`Suite::Canvas`), in `Suite::ALL` so the coordinator has it, in no other role's default list.
- `canvas_add_card { effort, kind, text? , ref? }`: adds to the effort's incoming. `kind` is `idea` or `question` with `text`, or a reference `{kind, id}` of a finding, source, decision, map or task. The effort defaults to the one the user last tagged (Unsorted if none).
- `canvas_link_cards { from, to, label? }`.
No tool moves, places, positions or deletes a card. Handlers sit in the core (`Core::tool`). Added to the tables in ADR 0016, the digest and the glossary, and one line to `config/roles/coordinator.md`.

## 5. GUI

- `core/model.ts` keeps the view shape. `core/view.ts` builds `canvases`, `cards`, `card_links`, `incoming` from the core snapshot. View ids: a card is `<kind letter><core id>` (`Q4`, `F90`), a canvas its number as text.
- `incoming` cards: `canvas_id` is the effort's first canvas; `under` is the card that links to it, if any (the strip's "goes under" line and the placement offset use it).
- `core/translate.ts` turns `place_card`, `drop_incoming`, `move_card`, `delete_card`, `add_card` into core commands; a new UI command `new_canvas` does `CreateCanvas` for the empty-canvas buttons.
- `pending.ts` loses canvases, cards, links, incoming and their actions; variants, reports, projects, status and colours stay.
- `MockCore` handles the same commands with small in-memory logic and its fixtures move into the core snapshot shape, so the browser dev server still shows the filled canvas.
- Pan, zoom and selection stay in `ui.ts`/React Flow. No change to look or keys.
